CM5 - RAG

Auteur·rice

Mikaël Valot

1 Introduction

Au CM4, Electrowl a trié ses mails avec un prompt. L’un d’eux demandait si un réfrigérateur pouvait être raccordé à une arrivée d’eau : il était classé autre, et personne n’y répondait. La réponse est pourtant dans le manuel du réfrigérateur.

Note

Electrowl veut un chatbot qui répond aux clients sur son site, 24 h sur 24, à partir de ses documents :

  • les 2 000 fiches produits ;
  • les manuels d’utilisation ;
  • les conditions de vente : livraison, retours, garanties.

Ces documents ne tiennent pas dans un prompt. Ce cours présente la solution : le RAG.

Le RAG est une technique pour construire un contexte spécifique à chaque requête, au lieu d’utiliser le même contexte pour toutes les requêtes.

  1. découper les documents en chunks (morceaux) ;
  2. rechercher (retrieval) les chunks utiles à une question ;
  3. générer la réponse : on envoie au LLM un prompt qui contient la question et ces chunks ;
  4. évaluer chaque étape.

1.1 Quand utiliser le RAG ?

On commence toujours par un prompt, et on le mesure. Si l’évaluation montre qu’il ne suffit pas, on essaie d’abord un modèle plus capable, puis une solution plus complexe. Il y en a trois, de la plus simple à la plus complexe : on ne passe au niveau suivant que si le précédent ne suffit pas.

Solution Quand l’utiliser Exemple chez Electrowl
Prompt Les consignes et les informations utiles tiennent dans la fenêtre de contexte. C’est le cas de nombreuses tâches : les modèles actuels lisent des centaines de milliers de tokens. Trier les mails : la procédure de tri tient en une page.
RAG (retrieval-augmented generation) Les documents sont trop nombreux pour le contexte, ou changent souvent : on cherche les passages utiles, puis on les met dans le prompt. Un chatbot qui répond aux clients avec les 2 000 fiches produits et les conditions de vente.
Fine-tuning On veut changer le format ou le style des réponses de façon constante, ou qu’un petit modèle fasse aussi bien qu’un gros sur une tâche précise. Pas pour ajouter des connaissances. Trier 1 million de mails par jour avec un petit modèle, entraîné sur 10 000 tickets déjà remplis.

Les agents ne sont pas un 4e niveau : c’est une autre façon d’utiliser un LLM, qui appelle des outils en boucle (chercher une commande, envoyer un mail, …). Ils seront vus à la séance 6.

Le fine-tuning est présenté à la fin de ce cours. Le reste du cours porte sur le RAG.

2 Principe du RAG

2.1 Activité : vrai ou faux

Voici trois réponses de gpt-oss-20b, le modèle du TP4, à des questions de clients d’Electrowl. Il n’a reçu aucun document. Pour chaque réponse, répondez à main levée : est-elle juste ?

Question A. Est-ce que je peux mettre du sel de cuisine dans mon lave-vaisselle Aquaris DW14 ?

« Oui, vous pouvez utiliser du sel de cuisine dans votre lave-vaisselle Aquaris DW14, mais il faut le faire avec précaution. »

Question B. Est-ce que vous livrez en Guadeloupe ?

« Oui, nous livrons en Guadeloupe. Délais : généralement 3 à 5 jours ouvrés après expédition. »

Question C. J’ai changé d’avis sur mon achat. Combien de temps ai-je pour le renvoyer ?

« Sur Electrowl, vous disposez de 14 jours calendaires à compter de la réception de votre colis. »

NoteRéponses

Les trois réponses sont fausses :

Question Document d’Electrowl
A Le manuel interdit le sel de cuisine : ses additifs abîment l’adoucisseur.
B Electrowl ne livre pas dans les départements d’outre-mer.
C Electrowl donne 30 jours, et non les 14 jours prévus par la loi.

Vous ne pouviez pas le savoir, et le modèle non plus : ces informations ne sont pas dans ses données d’entraînement. Il répond quand même, avec assurance : ce sont des hallucinations (CM3).

Un LLM ne connaît que ses données d’entraînement. Il lui manque :

  • les documents internes d’une entreprise, qui ne sont pas publiés sur Internet ;
  • les informations récentes : ses données s’arrêtent à une date, souvent plusieurs mois avant sa sortie ;
  • les informations qui changent : un prix, un stock, une procédure.

2.2 Rechercher, puis générer

Le RAG (retrieval-augmented generation), ou génération augmentée par la recherche, fonctionne en deux temps :

  1. on recherche les passages des documents qui répondent à la question ;
  2. on les place dans le prompt, et le LLM génère la réponse à partir d’eux.

Le modèle lit les documents dans son prompt, au moment de répondre.

  • Les paramètres W du modèle ne changent pas : le RAG n’est pas un entraînement.
  • Si Electrowl corrige un document, la réponse change dès la question suivante.
  • La réponse peut citer sa source : le client, ou un conseiller, peut la vérifier.

2.3 Fenêtre de contexte et RAG

Les modèles récents lisent 1 million de tokens. Pourquoi ne pas placer tous les documents dans le prompt ?

Critère Tous les documents dans le prompt RAG
Taille Les 2 000 fiches font plus de 400 000 tokens : elles dépassent les 131 000 tokens de gpt-oss-20b. Moins de 1 000 tokens par question, quelle que soit la taille du corpus.
Coût Tous les tokens sont payés à chaque question. Au TP5 : 670 tokens par question au lieu de 40 000, soit 40 fois moins cher.
Rapidité Plus le prompt est long, plus la réponse est lente. Une recherche de quelques dizaines de millisecondes, puis un prompt court.
Qualité Dans un contexte très rempli, le modèle retrouve moins bien l’information (CM3). Le modèle ne lit que les passages utiles, s’ils ont été trouvés.

Le RAG a un prix : il faut découper, indexer, chercher, et mesurer que la recherche trouve les bons passages.

AstuceEn pratique
  • Si tous les documents tiennent dans le prompt, pour un coût acceptable, n’utilisez pas de RAG : mettez-les dans le prompt (niveau 1).
  • Le RAG ajoute des connaissances au modèle sans l’entraîner : il convient aux informations internes, récentes ou qui changent.

3 Chunking

On ne cherche pas un document entier, mais un chunk (morceau) de document. Le chunking (découpage) sépare chaque document en chunks.

  • Un manuel parle de 10 sujets : installation, entretien, codes d’erreur, … La réponse à une question tient dans un paragraphe.
  • Un modèle d’embedding ne lit qu’un nombre limité de tokens : 128 pour celui du TP3, 512 pour celui du TP5. Le reste du texte est ignoré.
  • Moins on envoie de texte au LLM, moins la réponse coûte cher.

3.1 Méthodes de chunking

Méthode Principe Limite
Taille fixe Couper tous les 500 caractères, par exemple. Coupe au milieu d’une phrase ou d’un tableau.
Taille fixe avec overlap (recouvrement) Chaque chunk reprend la fin du précédent : une phrase coupée se retrouve entière dans l’un des deux. Du texte en double, donc plus de chunks.
Structure du document Un chunk par section, par paragraphe, ou par article d’un contrat. Demande des documents structurés. Les sections ont des tailles très différentes.

3.2 Contextualisation des chunks

Voici la section « Caractéristiques » d’une fiche produit, découpée par section :

Chunk : fiche du Polaris RS68, section Caractéristiques
## Caractéristiques

- Volume total : 634 litres, dont 225 litres pour le congélateur
- Niveau sonore : 36 dB
- Distributeur d'eau : oui, avec raccordement à une arrivée d'eau

De quel produit parle ce chunk ? Rien ne le dit, et les 2 000 fiches ont toutes une section semblable. Un chunk doit être compréhensible seul. On ajoute donc à chaque chunk le titre de son document :

Le même chunk, avec le titre du document en première ligne
Polaris RS68 : Réfrigérateur américain
## Caractéristiques

- Volume total : 634 litres, dont 225 litres pour le congélateur
...

Résultats mesurés au TP5, sur les 25 questions qui ont une réponse dans le corpus : la proportion de questions dont le bon passage est parmi les 3 premiers chunks trouvés.

Chunking Sans le titre Avec le titre du document
Taille fixe, 500 caractères, overlap de 100 68 % 96 %
Par section 56 % 100 %

Le chunking par section, mal appliqué, fait pire que la taille fixe : seule la mesure le montre.

3.2.1 Métadonnées

Une technique encore plus efficace est d’associer chaque chunk avec ses métadonnées : la source et le titre de son document, la section, la catégorie du produit, la date de mise à jour, des mots-clés. Elles peuvent être utilisées de deux façons :

  • dans le texte du chunk : on les ajoute au texte dont on calcule l’embedding, comme le titre au TP5 ;
  • comme filtre : la recherche compare la question aux seuls chunks qui ont la bonne métadonnée. Pour « Comment détartrer la Baristo E11 ? », elle ne cherche que dans les documents de l’E11, et ne peut plus renvoyer le manuel de l’E3.

Pour filtrer, il faut savoir de quel produit parle la question : une recherche par mots-clés sur la référence, ou un appel au LLM qui l’extrait.

3.2.2 Contexte généré par un LLM

Le titre du document ne suffit pas toujours. En taille fixe, un chunk du manuel du Roomy S7 peut commencer au milieu d’un tableau :

Chunk de taille fixe : manuel du Roomy S7
| Brosse principale | à démêler chaque semaine | tous les 6 mois |
| Brosse latérale | à nettoyer chaque mois | tous les 3 mois |

L’en-tête du tableau est dans le chunk précédent : « tous les 6 mois » désigne le remplacement de la brosse, mais le chunk ne le dit pas.

Le contextual retrieval demande à un LLM d’écrire, pour chaque chunk, une ou deux phrases qui le situent dans son document. Le LLM reçoit le document entier et le chunk. Son texte est ajouté au début du chunk, avant le calcul de l’embedding :

Le même chunk, avec le contexte généré en première ligne
Manuel du Roomy S7, section Entretien : tableau de l'entretien des pièces. La dernière colonne donne la fréquence de remplacement.
| Brosse principale | à démêler chaque semaine | tous les 6 mois |
| Brosse latérale | à nettoyer chaque mois | tous les 3 mois |
  • Anthropic, qui a publié la méthode, mesure 35 % d’échecs de recherche en moins sur ses jeux de test (Contextual Retrieval, 2024).
  • Le coût est payé à l’indexation : un appel au LLM par chunk, avec le document entier dans le prompt. Il faut refaire ces appels quand le document change.

3.3 Taille des chunks

  • Trop petit : le chunk perd son contexte. « Remplacez-le tous les 6 mois » ne dit plus de quelle pièce il s’agit.
  • Trop grand : le chunk parle de plusieurs sujets, son embedding représente mal chacun d’eux, et il coûte plus de tokens.

Il n’y a pas de taille idéale : elle dépend des documents et des questions. On en essaie plusieurs, et on mesure.

NoteDocuments réels : PDF, tableaux, images

Les documents d’Electrowl sont déjà du texte structuré. En entreprise, ce sont des PDF, des fichiers Word, des pages web, des scans.

  • Il faut d’abord en extraire le texte : les colonnes, les en-têtes et les pieds de page se mélangent, les tableaux perdent leur structure.
  • Les schémas et les photos ne sont pas lus. Un LLM multimodal peut les décrire, pour un coût plus élevé.
  • Cette étape prend souvent plus de temps que le reste du RAG : un texte mal extrait donne de mauvais chunks, quelle que soit la suite.
AstuceEn pratique
  • Découpez selon la structure du document quand il en a une, et ajoutez à chaque chunk le titre du document.
  • Gardez les métadonnées de chaque chunk (source, titre, produit, date) : elles servent à filtrer la recherche et à citer la source.
  • Si la mesure montre des chunks ambigus malgré le titre, essayez le contextual retrieval.
  • Lisez quelques chunks avant de continuer : si vous ne comprenez pas un chunk sans le reste du document, le modèle non plus.

4 Recherche

La recherche (retrieval) trouve les chunks utiles à une question.

4.1 Recherche sémantique

C’est la recherche du CM3 et du TP3 :

  1. un modèle d’embedding transforme chaque chunk en vecteur : des sens proches donnent des vecteurs proches ;
  2. il transforme la question en vecteur, de la même façon ;
  3. on calcule la similarité cosinus entre la question et chaque chunk ;
  4. on garde les \(k\) chunks les plus proches.

La recherche compare le sens : « enlever le calcaire » retrouve la section « Détartrage », alors que les mots sont différents.

question_embedding = embedder.encode_query(question, convert_to_tensor=True)
similarities = util.cos_sim(question_embedding, chunk_embeddings)[0]  # un score par chunk
scores, positions = torch.topk(similarities, k=5)                     # les 5 meilleurs

Le modèle d’embedding se choisit comme un LLM : on le mesure sur ses propres questions. Sur le corpus du TP5, découpé par section avec le titre, le modèle du TP3 (2020) trouve le bon passage pour 80 % des questions. Le modèle du TP5, de même taille, mais plus récent (2023) et entraîné pour la recherche, le trouve pour 100 % des questions.

4.2 Base de données vectorielle

Dans le TP5, les embeddings sont rangés dans un tenseur PyTorch : comparer une question à 750 chunks prend quelques millisecondes. Pour des millions de chunks, on utilise une base de données vectorielle (vector database).

Besoin Tenseur PyTorch Base de données vectorielle
Conservation en mémoire : tout est recalculé au redémarrage sur disque
Mise à jour recalculer le tenseur ajouter, modifier ou supprimer un chunk
Filtres à écrire soi-même par métadonnées : catégorie, date, langue, droits d’accès
Millions de chunks lent : la question est comparée à tous les chunks rapide : un index évite de tout comparer

Exemples : Chroma et Qdrant, ou l’extension pgvector, qui ajoute les vecteurs à une base PostgreSQL existante.

NoteRecherche approchée

Comparer la question à 100 millions de vecteurs prendrait plusieurs secondes. Une base vectorielle construit un index : elle regroupe les vecteurs proches, et ne compare la question qu’à une petite partie d’entre eux.

C’est une recherche approchée des plus proches voisins (approximate nearest neighbors, ANN) : beaucoup plus rapide, mais elle peut manquer un bon chunk de temps en temps. C’est un compromis entre vitesse et qualité, qui se règle.

4.3 Limites des embeddings

Les embeddings représentent le sens, et distinguent mal deux textes presque identiques :

  • deux références de produits : RS68 et RS86 ;
  • deux numéros de commande : CMD-481207 et CMD-481270 ;
  • un code d’erreur, un nom propre, un sigle rare.

Pour ces recherches, les mots-clés sont plus fiables : c’est la recherche plein texte d’un moteur de recherche classique. La recherche hybride (hybrid search) combine les deux : elle lance une recherche sémantique et une recherche par mots-clés, puis fusionne les résultats.

NoteReranking

Le reranking (reclassement) ajoute une étape : la recherche renvoie 50 chunks, puis un second modèle, plus lent et plus précis, lit la question avec chaque chunk et les reclasse. On garde les 5 premiers.

Cela améliore la qualité, pour un temps de réponse un peu plus long.

4.4 Nombre de chunks

\(k\) est le nombre de chunks envoyés au LLM.

  • \(k\) trop petit : le bon passage risque de ne pas être dans les résultats.
  • \(k\) trop grand : le prompt est plus long, donc plus cher et plus lent, et les chunks hors sujet peuvent tromper le modèle.

On cherche le plus petit \(k\) qui donne un bon taux de réussite.

4.5 Activité : quelle recherche ?

Pour chaque question d’un client, quelle méthode choisir : recherche sémantique, recherche par mots-clés, ou aucune recherche dans les documents ?

  1. « Ma machine à café fait un café sans goût, que faire ? »
  2. « Avez-vous encore la référence EW-87545 ? »
  3. « Où en est ma commande CMD-481207 ? »
  4. « Pouvez-vous reformuler votre réponse plus simplement ? »
NoteRéponses
  1. Sémantique : la question n’emploie pas les mots du manuel (« mouture », « réglage du broyeur »), mais elle en a le sens.
  2. Mots-clés : une référence exacte. Les embeddings confondraient EW-87545 avec une référence proche.
  3. Aucune recherche dans les documents : le statut d’une commande est dans la base de données des commandes. Il faut un agent, qui décide de consulter la base avec un outil (séance 6).
  4. Aucune : la réponse à reformuler est déjà dans la conversation. Chercher des documents n’apporterait que du bruit.
AstuceEn pratique
  • Commencez par une recherche sémantique simple, et mesurez-la. Ajoutez les mots-clés ou le reranking seulement si la mesure le demande.
  • Un tableau en mémoire suffit jusqu’à quelques centaines de milliers de chunks. Au-delà, ou si les documents changent souvent, prenez une base vectorielle.
  • Changer de modèle d’embedding oblige à recalculer tous les embeddings : ceux de deux modèles différents ne se comparent pas.

5 Génération

La génération est un prompt, comme au CM4 : une consigne, puis les chunks trouvés, puis la question.

messages = [
    {"role": "system", "content": prompt},
    {"role": "user", "content": f"""<documents>
<document source="manuels/aquaris_dw14.md">
Manuel d'utilisation : lave-vaisselle Aquaris DW14
## Sel régénérant et dureté de l'eau
... N'utilisez jamais de sel de cuisine : il contient des additifs qui abîment l'adoucisseur.
</document>
</documents>

Question du client : {question}"""},
]

Les techniques du CM4 s’appliquent. Quatre consignes sont propres au RAG :

Consigne Raison
« Réponds uniquement à partir des documents fournis. » Sans elle, le modèle complète avec ses connaissances générales, qui ne sont pas celles d’Electrowl.
« Si les documents ne contiennent pas la réponse, dis que tu n’as pas trouvé l’information. » Sans elle, le modèle invente quand la recherche a échoué.
« Vérifie que les documents parlent du produit demandé. » La recherche renvoie toujours les chunks les plus proches, parfois ceux d’un produit au nom voisin.
« Si tu as trouvé la réponse, termine par la source utilisée. » Le client ou un conseiller peut vérifier la réponse dans le document.

5.1 Quand les documents ne contiennent pas la réponse

Quand les documents trouvés ne contiennent pas la réponse, le prompt décide de ce qui se passe. Exemple mesuré au TP5, pour la question « Comment détartrer la machine à café Baristo E11 ? ». Le corpus ne contient pas le manuel de l’E11 : la recherche trouve celui de la Baristo E3, une machine à grains.

Prompt Réponse du chatbot
Sans consigne « Détartrage de la Baristo E11 : 1. Videz le bac à marc… 3. Maintenez la touche « Calc » pendant 5 secondes… » La procédure est celle de l’E3, une machine à grains. L’E11 est une machine à capsules.
Avec les consignes « Je n’ai pas trouvé d’instructions pour le détartrage de la Baristo E11. Pour obtenir la procédure, contactez notre service client. »

La seconde réponse oriente le client vers le service client, qui lui donnera la bonne procédure. Pour un service client, mieux vaut « je ne sais pas » qu’une réponse inventée.

5.2 Conversation

Un chatbot reçoit des questions qui dépendent des messages précédents :

Client : Le réfrigérateur Polaris RS68 peut-il être raccordé à une arrivée d’eau ?

Chatbot : Oui, le tuyau et le raccord sont fournis.

Client : Et il pèse combien ?

  • Le LLM n’a pas de mémoire (CM3) : on lui renvoie l’historique à chaque message.
  • La recherche, elle, ne voit que le dernier message : « il » ne nomme aucun produit, et elle renvoie des fiches sans rapport.
  • La solution est la reformulation de la question (query rewriting) : un premier appel au LLM réécrit la question à partir de l’historique, « Combien pèse le réfrigérateur Polaris RS68 ? », et c’est cette question qu’on recherche.
AstuceEn pratique
  • Délimitez les documents avec des balises, et indiquez la source de chacun.
  • Écrivez toujours ce que le modèle doit faire quand les documents ne contiennent pas la réponse.
  • Dans un chatbot, reformulez la question avant de chercher.

6 Evaluation

Un RAG a deux étapes, qui peuvent échouer chacune : on les évalue séparément, sur un dataset de questions étiquetées (CM4). Pour chaque question, on écrit à la main le passage qui contient la réponse, et la réponse attendue.

Étape Question posée Mesure
Recherche Le bon passage est-il parmi les \(k\) chunks trouvés ? le taux de réussite (hit rate) : la proportion de questions pour lesquelles c’est le cas
Génération La réponse est-elle juste ? la proportion de réponses correctes

Le taux de réussite est aussi appelé rappel à k (recall@k). Les outils d’évaluation de RAG mesurent aussi la précision du contexte (context precision) : la proportion des chunks envoyés au LLM qui sont utiles.

Les deux mesures ensemble disent où chercher l’erreur :

Bon passage trouvé Réponse juste Diagnostic
oui oui Tout va bien.
oui non Pb de génération : le prompt, ou un modèle trop faible.
non non Pb de recherche : le chunking, le modèle d’embedding, ou \(k\).
non oui Un coup de chance, ou une réponse que le modèle connaissait déjà.

Un score global ne suffit pas : si 20 % des réponses sont fausses, il ne dit pas s’il faut réécrire le prompt ou changer le chunking.

On mesure aussi le coût et la durée de chaque réponse : un client n’attend pas 30 secondes devant un chatbot.

6.1 LLM juge

Au CM4, on comparait un ticket à un ticket attendu avec ==. Ici, la réponse est une phrase : « Vous avez 30 jours » et « Le délai de retour est d’un mois » sont deux bonnes réponses.

Au début d’un projet, l’évaluation est manuelle : un expert du métier lit les réponses. Quand le dataset grandit et qu’on réévalue souvent, on utilise un LLM juge (LLM-as-a-judge) : un second appel à un LLM, qui reçoit la question, la réponse attendue et la réponse du chatbot, et qui dit si elle est correcte. Sa sortie est structurée (CM4) : une justification, puis correct.

  • Un juge se trompe aussi : avant de l’utiliser, on mesure son accord avec l’expert sur un échantillon. Ensuite, on relit régulièrement une partie de ses verdicts.
  • Chaque évaluation coûte un appel de plus par question.

6.2 Questions sans réponse

Le dataset doit contenir des questions dont la réponse n’est pas dans les documents : « Vendez-vous des trottinettes électriques ? ». La bonne réponse est « je n’ai pas trouvé cette information ». Sans ces questions, on ne mesure pas si le chatbot invente.

Les plus utiles portent sur un produit voisin : « Que signifie le code E21 sur le lave-linge Aquaris WM31 ? ». Le corpus ne contient pas le manuel du WM31, mais la recherche trouve celui du WM9, un autre lave-linge. Un prompt qui ne demande pas de vérifier le produit présente la réponse du WM9 comme valable pour le WM31.

AstuceEn pratique
  • Évaluez la recherche avant la génération : elle ne demande aucun appel au LLM, et une réponse ne peut pas être juste si le passage manque.
  • Lisez les erreurs une par une, avec les chunks trouvés : c’est là qu’on voit ce qu’il faut corriger.
  • Après chaque modification (chunking, modèle, \(k\), prompt), réévaluez tout le dataset, comme au CM4.

7 Limites

Données structurées. « Où en est ma commande CMD-481207 ? » n’a de réponse dans aucun document : elle est dans la base de données des commandes. Il faut une requête exacte, et non une recherche par le sens. Un RAG cherche à chaque question ; ici, il faut d’abord décider de consulter la base, puis vérifier que la commande appartient bien au client. C’est le rôle d’un agent, qui appelle un outil (séance 6).

Documents non fiables. Au CM4, le mail d’un client pouvait contenir une fausse consigne. Dans un RAG, c’est un document qui peut en contenir une : un avis de client, une page web, une fiche modifiée. Le modèle la lit dans son prompt, au milieu des autres chunks. C’est une injection de prompt indirecte : l’attaquant n’a même pas besoin de parler au chatbot.

Droits d’accès. Si le corpus contient des documents internes (marges, procédures, données de clients), le chatbot peut les citer à n’importe qui. Le filtre se fait à la recherche, par le programme, et non par une consigne dans le prompt : un chunk qui n’est pas dans le prompt ne peut pas fuiter.

Mise à jour. Un document modifié doit être redécoupé, et ses embeddings recalculés. Sinon, le chatbot répond avec l’ancienne version.

AstuceEn pratique
  • N’indexez que les documents que tous les utilisateurs du chatbot ont le droit de lire, ou filtrez la recherche selon l’utilisateur.
  • Un document est une donnée non fiable, comme un mail : le LLM propose, le programme vérifie (CM4).

8 Fine-tuning

Le fine-tuning est le 3e niveau. Il continue l’entraînement d’un modèle sur un petit dataset spécialisé : quelques centaines à quelques milliers d’exemples (prompt, réponse). Il modifie les paramètres, comme le post-training du CM3.

Dans quels cas faut-il fine-tuner ?

  • Utile si :
    • on souhaite un format ou un style constant ;
    • on veut qu’un petit modèle, rapide et bon marché, fasse aussi bien qu’un gros sur une tâche précise.
  • Inutile pour ajouter des connaissances qui changent (prix, stocks, procédures) : c’est le rôle du prompt ou du RAG.
  • Coûteux : il faut constituer le dataset, entraîner, puis tout recommencer quand une meilleure version du modèle de base sort.

Le fine-tuning n’est pas proposé pour tous les modèles propriétaires : si on sait dès le départ qu’on en aura besoin, cela oriente le choix vers un modèle open weights.

Electrowl essaiera le fine-tuning seulement si le volume de mails rend le prompt trop cher, et quand il aura des milliers de tickets déjà remplis pour entraîner le modèle.

AstuceEn pratique
  • Commencez toujours par un prompt. Beaucoup de projets n’ont pas besoin d’aller plus loin.
  • Le fine-tuning n’apprend pas de nouvelles connaissances au modèle de manière fiable : pour des informations, utilisez le prompt ou le RAG.

10 Points à retenir

Important
  1. Un LLM ne connaît pas les documents d’une entreprise : sans eux, il invente. Le RAG cherche les passages utiles, puis les place dans le prompt. Le modèle n’apprend rien : il lit.
  2. Si les documents tiennent dans le prompt pour un coût acceptable, on n’a pas besoin de RAG.
  3. Le chunking compte autant que le modèle : un chunk doit être compréhensible seul.
  4. La recherche sémantique compare le sens avec des embeddings. Elle distingue mal les références exactes : on la complète par des mots-clés.
  5. On évalue chaque étape : la recherche (le bon passage est-il trouvé ?), puis la réponse (est-elle juste ?).
  6. Le prompt dit quoi faire quand l’information manque : mieux vaut « je ne sais pas » qu’une réponse inventée.
  7. Un document est une donnée non fiable, et le chatbot peut citer tout ce qui est indexé.
